# HI Dataset Localization: Design

**Date:** 2026-10-16
**Repo:** `garda-ai-dataset` (new)
**Status:** Approved in brainstorming; awaiting spec review

## 1. Context

Garda AI trains a Multi-GNN fraud scorer and demos a real-time AML dashboard on IBM's synthetic AML data (Kaggle `ealtman2019/ibm-transactions-for-anti-money-laundering-aml`, generated by AMLworld). That data is multinational: 15 currencies, US payment formats, 30,470 fictional banks.

The current "Indonesian" copy in `garda-ai-data/HI-Small/` has no recipe behind it. It damages the data in several ways:

- Every currency was overwritten with `IDR`, which turned a model feature into a constant.
- Amounts were not converted per currency; the largest single transaction is Rp 276–467 T.
- Payment formats are still US-style.
- Entity names were replaced with person names, so IBM's company and individual markers are lost.
- `Patterns.txt` was never localized, so it no longer matches the transactions.
- All dates were shifted by exactly 3 years, which moved every transaction four weekdays later.

No public, labeled, transaction-level Indonesian dataset exists, because UU PDP 27/2022 and bank secrecy rules prevent it. The honest alternative is IBM's topology and labels, re-expressed in Indonesian terms with transforms that provably keep the laundering signal intact.

This spec is **sub-project 1 of 4**:

1. **Dataset** (this spec): layers 1–2 of the data contract, plus true motif labels.
2. **Training repo:** audit fixes, model outputs (score, fraud type, risk-factor codes) and the explainer.
3. **Insight Narrator:** an LLM turns explainer output into the four Indonesian narrative panels.
4. **Platform wiring:**
   - entity link fix and per-entity risk;
   - a transactions-by-entity endpoint;
   - real fraud type and explanation in the modals;
   - hiding the ground-truth label in the UI;
   - ingest reading `entities.csv`.

Typology injection (QRIS, e-wallet, judol, mule fan-in, pig-butchering) is a separate **spec #2**, after this one passes the F1 parity check.

## 2. Goals and non-goals

**Goals**

- Produce a deterministic, re-runnable localization of **HI-Small** (for the platform demo) and **HI-Medium** (for training) from the **original** Kaggle files.
- Use only transforms that preserve graph topology, edge order and labels.
- Keep the file format compatible with the existing consumers (`garda-ai-sim`, `garda-ai-ingest`, Multi-GNN `format_kaggle_files.py`). Switching the platform over is a one-line `GARDA_DATA_HOST_DIR` change.
- Add an entity profile file for the Users tab, and true per-transaction motif labels for later fraud-type prediction.
- Prove these properties with automated invariants on every build.

**Non-goals**

- Model outputs: fraud score, status, fraud type, risk factors, and entity risk score. These come from sub-project 2.
- LLM narratives. These come from sub-project 3.
- Per-transaction device, IP or geolocation. These are deliberately not synthesized; see §6.4.
- QRIS, e-wallet issuers, and new typologies. These come in spec #2.
- Any change to the backend, frontend, ingest, sim or deploy repos.
- HI-Large, and the LI-* variants.

## 3. The data contract (where each layer comes from)

| Layer | Examples | Produced by |
|---|---|---|
| 1. Transaction facts | time, banks, accounts, amount, currency, channel, label | **this repo** |
| 2. Account / entity profile | name, entity type, province, city, registration date, KYC, sector or occupation | **this repo** (display-only synthetic fields) |
| 3. Model outputs | fraud score, status, fraud type, risk-factor codes, entity risk | trained model (sub-project 2) |
| 4. Explanation | important neighbours and features, then an Indonesian narrative | explainer + LLM (sub-projects 2–3) |
| 5. Aggregates | totals, flag rate, monthly activity, fan-in and fan-out | backend (sub-project 4) |

Rule: the dataset never contains anything a model is supposed to infer. Otherwise the "AI" would be reading pre-written answers.

## 5. Outputs

Each dataset gets a folder `garda-ai-data/HI-<Size>-ID/`. `<X>` below means `HI-Small` or `HI-Medium`.

| File | Columns / content | Consumers |
|---|---|---|
| `<X>_Trans_sorted.csv` | The same 11 columns as IBM: `Timestamp, From Bank, Account, To Bank, To Account, Amount Received, Receiving Currency, Amount Paid, Payment Currency, Payment Format, Is Laundering`. Sorted by timestamp, with ties broken by original row number. | sim, Multi-GNN |
| `<X>_accounts.csv` | `Bank Name, Bank ID, Account Number, Entity ID, Entity Name, risk_score, risk_category` (same header as today) | ingest |
| `<X>_entities.csv` *(new)* | `Entity ID, Entity Name, Entity Type, Province, City, Registration Date, KYC Status, Sector` | backend / ingest (sub-project 4) |
| `<X>_Patterns.txt` | IBM format, with the same transforms applied as the transactions | humans, training |
| `<X>_typologies.csv` *(new)* | `transaction_id, attempt_id, motif` for laundering rows. `transaction_id` is the 1-based row ordinal in `_Trans_sorted.csv`, which is the same id the sim sends. Laundering rows not found in Patterns get motif `UNATTRIBUTED`. | training (sub-project 2) |
| `MANIFEST.json` | pipeline version, dataset, input sha256s, mapping-table sha256s, row counts, typology coverage, wall time | everyone |

**Risk columns are transitional.** `risk_score` and `risk_category` are model outputs (layer 3), so this pipeline does not invent them.

- For **HI-Small**, they are copied from the current `garda-ai-data/HI-Small/HI-Small_accounts.csv`, joined on `(Bank ID, Account Number)`. This keeps the Users tab working. Their provenance is unknown, and `MANIFEST.json` records `risk_source: "legacy-carryover"`.
- For **HI-Medium**, they are left empty. Ingest already accepts empty values.
- Sub-project 4 replaces both with model-computed, per-entity risk.
- If the legacy file is absent, Small also gets empty values and a warning.

**Why Small keeps its demo offsets.** No rows are added or removed, and every timestamp moves by a whole number of days. So the row counts per dataset day are unchanged, and the platform's `DEMO_SEED_SKIP`, `DEMO_SEED_LIMIT` and `DEMO_LIVE_SKIP` still land on day boundaries. Only the calendar dates in the deploy Makefile comments change (Sep 3–9 becomes Sep 6–12).

Rows that share a minute may be ordered differently from today's text-sorted file. That is harmless, because the platform is re-seeded from scratch when it switches.

## 6. Transforms

### 6.1 Rules every transform follows

- **Pure and deterministic.** The same input and mapping tables always produce byte-identical output. Randomness only ever comes from a hash-derived seed, keyed by `Entity ID` or `Bank ID`.
- **Never reads `Is Laundering`.** The orchestrator passes transforms a frame **without** the label column. The label is re-attached by row position just before writing.
- **The graph key is untouched.** `(Bank ID, Account Number)` keeps IBM's identity, so nodes never merge. This matters because 8 account numbers appear under more than one bank.
  - IBM's Trans file zero-pads bank IDs, and 58 banks appear with two spellings ("010" and "0010"). The output writes bank IDs as plain integers, matching `accounts.csv` and the platform.
  - On HI-Small this was verified to merge **0** `(bank, account)` keys. The validator re-checks it on every build (§8.3).
- **Columns are read by position.** IBM's Trans header names both account columns `Account`. The output header writes the second one as `To Account`, which is what the sim expects.

### 6.2 Transaction-level transforms

**FX (`fx_rates.csv`: currency, iso_code, idr_per_unit, rate_date, source)**

- There is one fixed rate per IBM currency, all for **2025-09-04** (the localized start date). No single source covers all 15 currencies, so each row records its source:
  - **ECB reference rates** (via frankfurter.dev): USD, EUR, CHF, CNY, ILS, INR, GBP, JPY, CAD, AUD, MXN, BRL.
  - **Central Bank of Russia** official rate: RUB.
  - **The USD peg (3.75)**: SAR.
  - **Yahoo Finance's BTC-USD daily close (110,723.60) × the ECB USD/IDR rate**: BTC.
- `Amount Paid` is multiplied by the rate for `Payment Currency`. `Amount Received` is multiplied by the rate for `Receiving Currency`.
- Both amounts are rounded to whole rupiah with Polars `round(0)`, and both currency columns become `IDR`.
- **No capping or clipping, ever.** Patterns where launderers keep amounts just under a threshold survive, because relative magnitudes within each currency are preserved.
- Rows that were cross-currency in IBM keep their slightly different paid and received IDR amounts. That is the conversion spread, and it is real.

**Channels (`channels.csv`: ibm_format, channel)**. A strict one-to-one rename:

| IBM | Indonesian channel |
|---|---|
| ACH | BI-FAST |
| Wire | RTGS |
| Cheque | SKNBI (Cek/BG) |
| Credit Card | Kartu Kredit |
| Cash | Setor/Tarik Tunai |
| Reinvestment | Pemindahbukuan |
| Bitcoin | Aset Kripto |

- An IBM format missing from the table is a hard error. No silent passthrough.
- QRIS and e-wallets are intentionally absent. Renaming IBM card payments to QRIS would put payments far above QRIS's Rp 10 juta limit on screen. Spec #2 adds them with real limits.

**Time.** A constant offset of **+1,099 days (157 whole weeks)**, so 2022-09-01 (Thursday) becomes 2025-09-04 (Thursday).

- Weekdays are preserved.
- The output keeps the IBM `YYYY/MM/DD HH:MM` format, which keeps text sorting chronological.

### 6.3 Institutions (`institutions.csv`: name, short_name, kind, group, weight)

`kind` is either `bank` or `crypto_exchange`.

- **Banks.** About 105 OJK-listed commercial banks, grouped as BUMN, Swasta Nasional, BPD, Bank Digital, Syariah and KCBA/Campuran. Each has a `weight` that approximates its share of accounts. The weights are an assumption, documented in the table.
- **Crypto exchanges.** Indodax, Tokocrypto, Pintu, and others.

The `Bank ID` itself is unchanged; only `Bank Name` is assigned. Assignment works in four steps:

1. Rank IBM banks by number of accounts, descending, breaking ties by `Bank ID`.
2. IBM banks named `Crytpo Bank #…` (IBM's own spelling) join the crypto-exchange pool; all others join the bank pool. The rule uses IBM's bank name, never the label.
3. Within each pool, walk the ranked list and fill institutions in descending weight order until each one's cumulative account share reaches its weight. Big IBM banks become big Indonesian banks.
4. Each IBM bank gets exactly one name. Many IBM banks share a name, which is realistic: one bank, many branches or BINs.

Real names are used, per the brainstorming decision. The dashboard's "Top Lembaga Fraud" therefore needs a *synthetic data* label, which is tracked in sub-project 4.

### 6.4 Entities and accounts

**Entity type** comes from IBM's original `Entity Name` prefix (`<Prefix> #<n>`). On HI-Small, every entity carries one of six prefixes:

| IBM prefix | HI-Small count | Indonesian type | Kind |
|---|---|---|---|
| Partnership | 189,683 | CV | business |
| Corporation | 172,351 | PT | business |
| Sole Proprietorship | 149,048 | UD | business |
| Country | 6,692 | Lembaga | business |
| Individual | 740 | Perorangan | individual |
| Direct | 67 | Lembaga | business |

- CV is the usual Indonesian partnership form, so it replaces the Firma from the brainstorm.
- What IBM means by "Country" and "Direct" is undocumented. The "Country" entities own accounts at IBM's crypto banks. Both map to the generic `Lembaga`.
- The table lives in `mappings/entity_types.csv`. An unknown prefix is a hard error (exit 3), so there is no synthetic fallback.

**Names** use Faker's `id_ID` locale, seeded by `sha256(Entity ID)`:

- Perorangan: a person name.
- PT, CV, UD: `PT/CV/UD <surname> <suffix>`, for example `PT Wibisono Sejahtera`.
- Lembaga: `Lembaga <surname> <suffix>`.

Every account of an entity shows that entity's name.

**Profile fields** are display-only. They are never model features, and they never read the label:

| Field | Rule |
|---|---|
| Province | **The exact `garda-ai-ingest` algorithm** (sha256 of Entity ID into a weighted bucket of 15 provinces), so it matches what the platform shows today. |
| City | A second hash picks from `provinces_cities.csv`, which lists the major cities of each province. |
| Registration Date | The entity's first appearance in any transaction (as sender or receiver), minus a hash-seeded 30 days to 10 years. It is always before the first transaction. |
| KYC Status | `kyc_status.csv` weights: Terverifikasi, Perlu Pembaruan, Dalam Review. The weights are an assumption. |
| Sector | Companies get a business sector; Perorangan get an occupation. Both come from `sectors_occupations.csv`. |

**Deliberately not synthesized:** per-transaction device, IP and geolocation. Data generated independently of fraud would carry zero signal, and data correlated with fraud would be label leakage. Risk chips that need them ("Device Mismatch", "Geographic Anomaly") are dropped from the target vocabulary. All chips must come from real graph signals.

### 6.5 Patterns and motif labels

- `Patterns.txt` is parsed into attempts: a `BEGIN LAUNDERING ATTEMPT - <MOTIF>: <detail>` header, CSV rows, then an `END` line.
- Each row is matched to the raw Trans file **before** localization, on the exact raw line text of all 11 fields. A 200-row sample on HI-Small matched byte for byte.
  - Matching only considers rows with `Is Laundering = 1`. `typologies.csv` is a label product by design, so reading the label here is allowed.
  - Duplicate rows are matched as a multiset.
- Matched rows get `attempt_id` (sequential, in file order) and `motif` (the header token, e.g. `FAN-OUT`, `CYCLE`, `GATHER-SCATTER`).
  - HI-Small has 370 attempts across 8 motifs and 3,209 pattern rows, against 5,177 laundering rows. At most 62% of laundering rows can get a motif; the rest are `UNATTRIBUTED`.
- The localized `Patterns.txt` copies each matched row's **already-localized Trans line**, so the two files can never disagree. Header and END lines are kept verbatim.
- Coverage is recorded in the manifest: matched laundering rows out of all laundering rows, and unmatched pattern rows. Unmatched pattern rows fail validation.

## 7. Fetch

- Downloads **individual files** through the Kaggle API, never the whole 34 GB dataset. Small is about 0.5 GB; Medium is about 3.2 GB.
- Credentials come from `GARDA_KAGGLE_JSON` (default `~/.kaggle/kaggle.json`). The file is never copied into the repo and never logged.
- Each file's sha256 is recorded in `garda-ai-data/raw/<X>/SHA256SUMS`.
- Re-running skips files whose hash still matches. A mismatch is a hard error that tells you to delete the file and re-fetch.

## 8. Validation (invariants)

`garda-dataset validate --dataset <x>` runs automatically at the end of `localize`. Any violation fails with exit code 1. The checks:

1. **Row count:** output rows equal raw rows.
2. **Labels:** after mapping each sorted row back to its original row, `Is Laundering` is identical for every row.
3. **Graph keys:** `(From Bank, Account)` and `(To Bank, To Account)` are identical per row, with bank IDs compared as integers. The number of distinct `(bank, account)` keys is the same before and after integer normalization, so no nodes merged.
4. **FX:** for every row, `new_amount == round(raw_amount × rate[raw_currency])`, for both paid and received.
5. **Time:** for every row, `new_ts − raw_ts == 1,099 days`, and the output is non-decreasing in time.
6. **Channels:** every row's channel equals `channels[raw_format]`.
7. **Label independence:** take the first 200,000 raw rows, **invert** `Is Laundering` on every row, and re-run the in-memory localize. Every non-label output column must be byte-identical.
   - Inverting changes every label. A shuffle of a sample with no laundering rows would change nothing and pass vacuously.
   - The same check runs on the full fixture in tests.
8. **Patterns:** every pattern row matches a Trans row. Typology coverage is reported.
9. **Entities:**
   - every account's entity exists in `entities.csv`;
   - `Registration Date` is before the entity's first transaction;
   - every institution name comes from `institutions.csv`.
10. **Manifest:** the input and mapping hashes in `MANIFEST.json` match the files on disk.

The validator also prints a **distribution report** (not pass/fail) to support the judges' story: amount percentiles per channel, rows per channel and per institution group, entity-type mix, and laundering rate per channel.

## 9. Performance and memory

The development machine has 16 GB of RAM and about 65 GB of free disk.

- Polars **lazy and streaming** mode is used throughout. The raw Trans file is scanned, not loaded.
- **Small:** target under 2 minutes end-to-end.
- **Medium (about 32M rows)** is processed in two passes, and the same code runs for Small:
  1. **Pass 1 streams** the raw file through the transforms into a temporary Parquet file.
  2. **Pass 2 handles one dataset day at a time:** it filters that day from the Parquet, sorts it by `(timestamp, original_row)` in memory, and appends it to the output CSV. Memory is bounded by the largest day, about 22% of rows.
  - The validator works per day in the same way, so a global sort or join over 32M rows is never needed.
- **Disk:** Medium needs about 3.2 GB raw, plus about 3.2 GB output, plus temporary files. That is checked before starting, and the run fails early if fewer than 10 GB are free.

## 10. Error handling and exit codes

The scheme matches the other repos:

| Code | Meaning |
|---|---|
| `0` | OK |
| `1` | Validation failed |
| `2` | Raw input missing, or hash mismatch |
| `3` | Mapping table invalid (unknown currency or format, malformed CSV, a non-positive weight, or a comma inside a name) |
| `4` | Fetch or credentials error |
| `5` | Insufficient disk |

Error messages name the file and row or key involved, never credential values.

## 11. Testing

- **Fixtures.** Hand-made raw files of about 50 transactions, 20 accounts and 3 laundering attempts. They cover:
  - multiple currencies, including Bitcoin and a cross-currency row;
  - every IBM payment format;
  - a duplicate account number across two banks;
  - an entity with several accounts;
  - same-minute ties;
  - duplicate identical transaction rows.
- **Unit tests** for each transform:
  - FX exactness and rounding;
  - unknown currency or format raises an error;
  - institution assignment is rank-preserving and deterministic;
  - entity type from IBM prefixes, and the fallback;
  - registration date is always before first seen;
  - Patterns parsing and multiset matching.
- **Validator mutation tests.** Each invariant in §8 gets a test that corrupts exactly one output value and asserts that the validator catches it. This proves the checks are not vacuous.
- **Determinism test:** running localize twice gives byte-identical outputs.
- **Label-independence test:** inverting every label on the fixture leaves non-label outputs identical.
- **Tooling:** ruff and mypy `--strict`, matching the other repos.

## 12. Acceptance criteria

- `make all DATASET=small` and `make all DATASET=medium` both complete, with every invariant in §8 passing.
- `MANIFEST.json` for each dataset records the hashes and the typology coverage.
- **Consumer smoke test:**
  - the sim's reader parses `HI-Small-ID/HI-Small_Trans_sorted.csv`;
  - the ingest seed parses `HI-Small-ID/HI-Small_accounts.csv`;
  - Multi-GNN's `format_kaggle_files.py` runs on `HI-Small-ID/HI-Small_Trans_sorted.csv`.
  All three are run read-only against their current code, with no changes to those repos.
- A README explains how to reproduce the data, what is synthetic, and the suggested statement for judges.

**Out of scope here, handed to sub-project 2:** retraining Multi-GNN on the original and localized Small data, and checking that minority-class F1 stays within seed noise.

## 13. Assumptions to verify on first download

1. ~~IBM's original `Entity Name` values carry company and individual markers.~~ **Verified on HI-Small:** 6 prefixes (§6.4).
2. ~~`Patterns.txt` covers most laundering rows.~~ **Verified on HI-Small:** at most 62% coverage. Actual coverage is recorded in the manifest and accepted as-is.
3. HI-Medium's currency and payment-format vocabulary equals HI-Small's. Any new value is a hard error, and the fix is to add a mapping row.
4. Exact HI-Medium row, account and laundering counts. These are recorded in the manifest.
